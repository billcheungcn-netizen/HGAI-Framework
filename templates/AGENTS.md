## 2. 面向项目负责人的沟通硬规则

项目负责人不一定是专业程序员。需求确认、计划摘要和完成反馈必须优先使用终端用户语言。

完成反馈固定说明：

1. 做成了什么功能；
2. 功能满足了什么需求；
3. 终端用户怎样使用；
4. 页面、状态或流程怎样变化；
5. 最终给用户带来了什么；
6. 怎样从用户角度确认可用。

不得以专业术语、代码、函数名和文件清单代替功能说明。详细规则：`docs/rules/user-facing-communication.md`。

字段角色：

- `[人审-用户]`：项目负责人只审核功能、需求、使用、可见变化和用户收益；
- `[人授权]`：项目负责人决定依赖、数据迁移、远端推送、发布等高影响动作；
- `[AI交叉审-技术]`：由第二个 AI 或独立只读审核检查模块、架构、测试、安全和回退；
- `[工具证明]`：由测试、CI、构建、扫描和 Git 产生真实证据；
- `[自动维护]`：由 AI 更新文档、索引、术语和交接记录。

## 3. 强制工作流程

1. 阅读本文件、`docs/rules/INDEX.md` 和适用规则；
2. 检查 `docs/coordination/ACTIVE_TASKS.md`，生成唯一任务 ID 并认领写入范围；
3. 查 `GLOSSARY.md`，用统一术语复述终端用户需求；
4. 按 Token 定位阶梯从文件、模块到受限搜索逐级定位；
5. 默认建立 `TASK_LITE`，高风险任务建立完整 `TASK`，Bug 使用 `BUG`；
6. 编码前写出用户可见结果、目标文件、禁止范围、测试、机器门禁和 Git 计划；
7. 人审核用户方向并授权高影响动作；技术项由第二 AI 或独立只读审核复核；
8. 记录 Git 基线并保护用户未提交修改；
9. 功能代码与自动化测试同批执行；
10. 运行统一本地验证，并在适用时等待远端 CI；
11. 建立授权范围内的 Git 检查点和私有远端备份；
12. 更新任务、索引、模块地图、术语表、规则和任务认领；
13. 使用终端用户视角分别报告本地验证、CI、合并和发布状态。

无法确定责任模块、测试方法或用户结果时，停止编码并先完成定位。

## 4. 架构硬约束

- 模块化设计；
- 依赖必须遵循：`<填写本项目单向依赖规则>`；
- 高内聚、低耦合；
- 一个职责只有一个权威实现；
- 展示层不得复制或承担业务逻辑；
- 未经批准不得增加兜底、兼容、双写或第二套实现；
- 不得跨模块顺手修改无关代码；
- 必须优先修复根因；
- 实际结构与文档不一致时暂停并调查。

详细规则：`docs/rules/architecture-boundaries.md`。

## 5. 测试硬约束

- 行为变化必须新增或更新自动化测试；
- Bug 修复优先先建立失败复现测试；
- 测试代码与功能代码同批入库；
- 所有通过结论必须来自真实执行；
- 无测试体系时必须登记缺口并建立测试基础设施任务；
- 无法自动化时记录原因、人工步骤、证据和后续计划。

测试现状：`docs/system/TESTING.md`。详细规则：`docs/rules/testing.md`。

机器门禁：`docs/rules/automation-gates.md`。本地钩子可以被绕过，正式项目以绑定具体 Commit 的远端 CI 为更强证据。

- **[人授权] AI Git 权限：** `<禁止提交 / 可提交已验证检查点 / 每次提交前询问>`
- **[人授权] 远端策略：** `<禁止 / 仅私有备份分支 / 允许推送检查点 / 允许审核后合并>`
- 分支命名：`task/<ID>-<简述>`、`bug/<ID>-<简述>`、`refactor/<ID>-<简述>`；
- Commit message：`[任务ID] <用户功能或验证检查点>`；

- 不得覆盖用户未提交修改；

- 推送前确认远端地址、仓库可见性和密钥扫描结果；
- 本地通过、CI 通过、已合并和已发布必须分别记录。

## 7. 多 AI 协作

- 任务 ID：`TYPE-YYYYMMDD-HHMMSS-AGENT-XXXX`；
- 写入前登记 `docs/coordination/ACTIVE_TASKS.md`；
- 与其他 active 任务模块或文件重叠时暂停；
- 审核 AI 默认只读，并把结论写入 REVIEW 文档；
- 严格模式在可用时优先使用不同 AI 技术交叉审核；
- 初始化文档在投入高风险开发前应由第二个 AI 对照真实代码复核。

详细规则：`docs/rules/multi-agent-coordination.md`。

## 8. Token 与检索成本

定位顺序：`指定文件 → 指定模块 → 用户现象 → 受限搜索 → 全仓搜索`。只有证据表明当前范围不足时才能扩大一级，并在任务文档记录原因。

详细规则：`docs/rules/token-management.md`。

## 9. 依赖与密钥

- 未经批准不得引入新依赖；
- 必须审查版本、维护状态、许可证、权限和锁文件；
- 密钥、Token、密码、私钥和 OAuth 凭据不得进入代码、日志、文档、聊天和 Git；
- 发现疑似密钥立即停止，不复述其内容。

详细规则：`docs/rules/dependencies-and-secrets.md`。

## 13. 必须暂停并报告

- 实际代码、文档和规则相互冲突；
- 不能说明终端用户最终获得什么；
- 计划选错责任模块或必须跨层才能继续；
- 必须增加未经批准的兜底、兼容、双写或第二套实现；
- 修改范围明显超过计划；
- 行为变化没有测试，且没有记录例外理由；
- 测试失败或根因仍不明确；
- 发现疑似密钥；
- 需要新依赖但尚未批准；
- Git 操作可能覆盖用户修改。
- 其他 active 任务已认领相同模块或文件；
- 严格任务缺少要求的交叉审核或远端 CI 证据；
- 无法区分本地通过、CI 通过、已合并和已发布状态。
