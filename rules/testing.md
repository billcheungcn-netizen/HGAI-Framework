# 测试交付规则

## 硬性要求

- 所有可观察行为变化必须新增或更新自动化测试；
- 所有 Bug 修复优先先建立修复前失败的复现测试，再修到通过；
- 测试代码与功能代码同批交付并进入仓库；
- 重构必须证明外部行为未被意外改变；
- 所有“通过”结论必须来自实际执行结果。

## 没有测试体系时

不能只在模板中填写“测试命令”。必须：

1. 记录当前测试缺口；
2. 为当前风险提供确定性人工验证；
3. 建立测试基础设施任务；
4. 对核心路径优先补最小可运行测试；
5. 在 `docs/system/TESTING.md` 记录真实能力和计划。

## 暂时无法自动化时

记录：

- 无法自动化的原因；
- 可重复人工步骤；
- 预期和实际结果；
- 截图、日志或其他证据的位置；
- 后续自动化任务和优先级。

“时间不够”不能作为永久不测试的理由。

## 验证顺序

1. 从终端用户角度验证功能；
2. 运行新增或修改的针对性测试；
3. 运行相关模块回归测试；
4. 运行项目要求的构建、类型检查和静态检查；
5. 检查架构边界和未预期副作用。

## 机器门禁

测试规则必须通过 `automation-gates.md` 落到统一验证命令、提交钩子和适用的远端 CI。AI 的文字声明、未执行的测试命令和仅创建但未运行的 CI 配置都不能算通过证据。
