## 2. 面向项目负责人的沟通硬规则

项目负责人不一定是专业程序员。需求确认、计划摘要和完成反馈必须优先使用终端用户语言。

完成反馈固定说明：

1. 做成了什么功能；
2. 功能满足了什么需求；
3. 终端用户怎样使用；
4. 页面、状态或流程怎样变化；
5. 最终给用户带来了什么；
6. 怎样从用户角度确认可用。

不得以专业术语、代码、函数名和文件清单代替功能说明。详细规则：`docs/rules/user-facing-communication.md`。

## 3. 强制工作流程

1. 阅读本文件、`docs/rules/INDEX.md` 和适用规则；
2. 查 `GLOSSARY.md`，用统一术语复述终端用户需求；
3. 根据文档索引和模块地图定位责任模块；
4. 默认建立 `TASK_LITE`，高风险任务建立完整 `TASK`，Bug 使用 `BUG`；
5. 编码前写出用户可见结果、目标文件、禁止范围、测试和 Git 计划；
6. 人只审核方向性字段，其他内容由 AI 自动维护；
7. 记录 Git 基线并保护用户未提交修改；
8. 功能代码与自动化测试同批执行；
9. 运行真实验证，建立授权范围内的 Git 检查点；
10. 更新任务、索引、模块地图、术语表和规则；
11. 使用终端用户视角反馈成果。

无法确定责任模块、测试方法或用户结果时，停止编码并先完成定位。

## 4. 架构硬约束

- 模块化设计；
- 依赖必须遵循：`<填写本项目单向依赖规则>`；
- 高内聚、低耦合；
- 一个职责只有一个权威实现；
- 展示层不得复制或承担业务逻辑；
- 未经批准不得增加兜底、兼容、双写或第二套实现；
- 不得跨模块顺手修改无关代码；
- 必须优先修复根因；
- 实际结构与文档不一致时暂停并调查。

详细规则：`docs/rules/architecture-boundaries.md`。

## 5. 测试硬约束

- 行为变化必须新增或更新自动化测试；
- Bug 修复优先先建立失败复现测试；
- 测试代码与功能代码同批入库；
- 所有通过结论必须来自真实执行；
- 无测试体系时必须登记缺口并建立测试基础设施任务；
- 无法自动化时记录原因、人工步骤、证据和后续计划。

测试现状：`docs/system/TESTING.md`。详细规则：`docs/rules/testing.md`。

- 未经批准不得引入新依赖；

- 发现疑似密钥立即停止，不复述其内容。

## 11. 必须暂停并报告

- 实际代码、文档和规则相互冲突；
- 不能说明终端用户最终获得什么；
- 计划选错责任模块或必须跨层才能继续；
- 必须增加未经批准的兜底、兼容、双写或第二套实现；
- 修改范围明显超过计划；
- 行为变化没有测试，且没有记录例外理由；
- 测试失败或根因仍不明确；
- 发现疑似密钥；
- 需要新依赖但尚未批准；
- Git 操作可能覆盖用户修改。
