# 终端用户视角沟通规则

## 目的

让项目负责人即使不是专业程序员，也能理解需求、判断方向和确认功能是否完成。

## 核心原则

- 内部开发文档可以包含技术细节；
- 面向项目负责人的主反馈必须先使用终端用户语言；
- 不假设项目负责人懂代码、架构、框架或专业术语；
- 技术修改必须翻译成用户能够观察和使用的功能变化；
- 如果没有可见页面，描述命令、自动流程、数据、通知或行为变化。

## 需求确认时必须说明

1. 终端用户当前遇到什么问题；
2. 用户需要什么功能；
3. 用户会怎样进入和使用它；
4. 成功后页面、状态或流程应该怎样变化；
5. 哪些结果不属于本次需求。

## 完成反馈的固定顺序

1. **功能名称**：给功能一个用户能够理解的名字；
2. **功能说明**：它是什么，而不是改了哪些文件；
3. **满足的需求**：解决项目负责人或终端用户什么问题；
4. **使用方法**：用户从哪里进入、执行什么操作；
5. **可见变化**：页面、按钮、提示、数据、状态或流程怎样变化；
6. **用户收益**：更快、更清楚、更稳定、少做什么或避免什么；
7. **验收方法**：使用用户操作验证，而不是只报测试命令；
8. **注意事项**：只有真实存在时才写。

## 禁止

- 不得以文件清单、函数名、代码行数或框架术语作为主成果；
- 不得用“重构了服务层”“增加了状态管理”等表述代替功能说明；
- 不得在用户说明中穿插大段代码；
- 不得只说“已完成、测试通过”，却不说明用户获得了什么；
- 不得因为功能属于后台或基础设施，就省略终端用户影响。

## 技术附录

只有在项目负责人主动询问、必须做技术决策、验证失败、任务未完成或需要其执行技术操作时提供。技术附录放在用户功能说明之后。

## 翻译示例

不要只说：

```text
重构了认证状态机并增加 refresh token 互斥锁。
```

应先说：

```text
登录保持功能已经完善。用户长时间停留在页面后继续操作时，系统会自动维持登录状态，不会再同时弹出多个登录请求，也不会因为凭据刷新冲突被迫重新登录。
```

如有必要，再在技术附录说明实现方式。
