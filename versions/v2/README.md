# AI 大型软件开发控制法 V2

> 依据 `vibecoding.mp4` 中作者的实践方法提炼，并吸收实际审核意见升级。V1 原版保存在 `versions/v1/`。

## 一、这套控制法解决什么

这不是“一句话生成软件”的提示词，而是一套让人长期操控 AI 开发、维护和重构软件的方法。

它解决七类常见失控：

- AI 忘记以前做过什么；
- 项目变大后找错模块或修改错误文件；
- 用兜底、兼容和重复实现快速糊住问题；
- 文档、代码、测试和 Git 历史相互脱节；
- 文档越积越多，最后反过来成为幻觉源；
- 模糊检索导致 Token 和开发成本持续上升；
- AI 完成了技术修改，却无法用项目负责人和终端用户能理解的语言说明成果。

完整闭环：

```text
恢复项目认知
→ 索引并精确定位
→ 书面计划
→ 人检查方向
→ 建立可回退基线
→ 受控执行并同步产出测试
→ 验证用户行为和技术结果
→ 提交可追溯 Git 检查点
→ 更新唯一权威文档与规则
→ 用终端用户语言反馈成果
→ 审计架构并持续重构
```

## 二、角色分工

### 人负责

- 说明真正要解决的用户问题；
- 确认 AI 是否理解了需求；
- 检查责任模块、架构方向和禁止范围；
- 判断功能是否真的满足项目负责人或终端用户；
- 决定高风险方案、第三方依赖、密钥权限和 Git 发布动作。

人不需要是专业程序员，也不应被迫阅读大量代码和术语才能判断任务是否完成。

### AI 负责

- 读取索引、历史文档、规则和代码；
- 自动填写任务、Bug、测试和交接文档；
- 提出文件级计划；
- 编写代码和自动化测试；
- 执行验证并记录真实证据；
- 维护索引、模块地图、术语表和规则库；
- 把技术修改翻译成终端用户能够理解的功能变化。

### 工具负责

- Git 记录可回退检查点；
- 测试、构建、类型检查和静态检查提供可重复证据；
- CI、锁文件和密钥扫描提供持续约束。

## 三、八条核心原则

### 1. 外挂记忆

每个需求、Bug、开发计划、关键判断、执行结果和教训都写入项目文档。不能依赖某次对话仍然存在。

### 2. 索引先行

项目根目录的 `AGENTS.md` 是 AI 的第一入口。AI 必须先通过索引找到相关文档、规则、模块和代码，不得默认扫描全仓。

### 3. 计划先于编码

任何任务先形成书面计划，把需求理解、目标模块、目标文件、禁止范围、用户行为和验证方法暴露出来，再开始修改。

### 4. 架构负面约束

持续强调模块化、单向依赖、高内聚低耦合、业务边界、禁止未经批准的兜底和兼容、禁止重复实现。不能假设模型已经记住这些要求。

### 5. 测试与功能同批交付

功能变化必须新增或更新自动化测试。Bug 修复优先先形成可失败的复现测试，再修到通过。测试代码与功能代码属于同一任务、同一证据链。

### 6. Git 是真实的代码证据链

任务文档、代码修改、测试结果和 Git Commit 必须通过任务 ID 相互关联。高风险重构在独立分支和已验证基线上进行，跑偏时恢复到干净检查点，不让 AI 凭记忆“改回来”。

### 7. 文档和规则必须防腐

同一事实只有一个权威来源。所有文档有状态、更新时间、替代关系和关联 Commit。主索引只保留当前有效内容，过期内容进入归档，不能让 `AGENTS.md` 无限增长。

### 8. 面向项目负责人的沟通必须使用终端用户语言

内部过程可以包含文件、模块、接口、测试和代码；对项目负责人的主反馈默认必须说明：

1. 做成了什么功能；
2. 这个功能是什么；
3. 满足了项目负责人或终端用户什么需求；
4. 用户如何使用；
5. 页面、状态或操作流程发生了什么变化；
6. 最终给用户带来了什么结果；
7. 怎样用用户能够理解的方式验证。

除非对方主动要求技术细节，否则不得在主反馈中堆专业术语、代码片段、文件清单或实现过程。不能假设项目负责人本身是专业程序员。

## 四、推荐项目结构

```text
项目根目录/
├─ AGENTS.md                         # Codex 和通用 AI 第一入口
├─ CLAUDE.md                         # Claude Code 适配入口
├─ .cursor/rules/                    # Cursor 适配入口
│  └─ ai-project-control.mdc
├─ docs/
│  ├─ INDEX.md                       # 全量文档登记与归档入口
│  ├─ system/
│  │  ├─ PROJECT.md                  # 项目目标、用户、功能和非目标
│  │  ├─ ARCHITECTURE.md             # 分层、边界和依赖方向
│  │  ├─ MODULE_MAP.md               # 从需求或现象定位模块与文件
│  │  ├─ GLOSSARY.md                 # 统一终端用户与代码术语
│  │  └─ TESTING.md                  # 测试现状、命令和缺口
│  ├─ rules/
│  │  ├─ INDEX.md                    # 常驻规则索引
│  │  ├─ user-facing-communication.md
│  │  ├─ git-workflow.md
│  │  ├─ testing.md
│  │  ├─ document-governance.md
│  │  ├─ dependencies-and-secrets.md
│  │  ├─ architecture-boundaries.md
│  │  └─ bug-diagnosis.md
│  ├─ tasks/active/
│  ├─ tasks/completed/
│  ├─ bugs/active/
│  ├─ bugs/completed/
│  ├─ refactors/
│  ├─ decisions/
│  ├─ audits/
│  ├─ handoffs/
│  └─ archive/
└─ 源代码目录/
```

`docs/rules/` 是常驻规则的唯一权威来源。`AGENTS.md`、`CLAUDE.md` 和 `.cursor/rules/*.mdc` 只作为工具适配入口，不各自维护一套互相冲突的规则。

## 五、文档字段责任

模板统一使用以下标记：

- **`[AI填写]`**：AI 根据真实项目自动生成，人不必手写；
- **`[人审]`**：AI 先写，人只检查方向和结果；
- **`[工具生成]`**：由 Git、测试或构建命令产生，不能凭空填写；
- **`[自动更新]`**：任务结束时由 AI 同步更新。

原则是：**文档由 AI 写，人只看方向性字段和终端用户结果。**

## 六、三种工作模式

### 快速模式：默认

适用于范围明确、低风险、可快速验证的修改，使用 `TASK_LITE.md`。

```text
索引 → 轻量计划 → 人快速看用户结果和目标模块
→ 代码与测试 → 验证 → Git 检查点 → 更新索引 → 用户视角反馈
```

### 严格模式

适用于新模块、核心业务、跨模块修改、数据迁移、安全事项和高风险 Bug，使用完整 `TASK.md`。

```text
恢复认知 → 深入定位 → 完整计划 → 人批准
→ 独立分支或基线 → 分检查点执行 → 自动化测试
→ 完整验证 → 文档与 Git 关联 → 用户视角反馈
```

### 重构模式

适用于 AI 多次找错模块、依赖混乱、兜底增加、文档腐化或 Token 明显上升。

```text
建立已验证基线 → 独立重构分支 → 架构审计
→ 目标结构 → 分步重构和测试 → 每步提交
→ 删除旧实现 → 更新模块地图和规则 → 用户影响说明
```

## 七、标准任务闭环

### 阶段 0：恢复项目认知

AI 阅读 `AGENTS.md`、当前有效规则、项目架构、模块地图、术语表和相关历史文档。

### 阶段 1：用用户语言确认需求

先说明终端用户现在遇到什么问题、期望拥有什么功能、怎样使用以及成功后看见什么。业务术语先查 `GLOSSARY.md`，不允许自行猜测。

### 阶段 2：精确定位

根据 `MODULE_MAP.md` 找到责任模块、目标文件、调用入口和禁止修改范围。不能定位时继续调查，不立即编码。

### 阶段 3：建立任务文档

低风险任务使用 `TASK_LITE.md`，高风险任务使用 `TASK.md`。AI 自动填写，人只审用户结果、责任模块、禁止范围、风险和验收标准。

### 阶段 4：建立 Git 基线

记录当前分支、工作区状态和基线 Commit。不得覆盖尚未提交的用户修改。高风险任务按项目授权创建任务分支。

### 阶段 5：受控执行并产出测试

代码、测试、文档同步修改。实际情况与计划不符时暂停并更新计划，不擅自扩大范围，不用兜底隐藏根因。

### 阶段 6：验证

先验证终端用户行为，再执行自动化测试、构建、类型检查、静态检查和架构检查。所有结果必须来自真实工具输出。

### 阶段 7：Git 检查点

在获得项目授权后，把经过验证的代码和测试提交为一个或多个可回退检查点。Commit message 引用任务 ID，不混入无关任务。

### 阶段 8：更新项目记忆

更新任务文档、模块地图、术语表、文档登记表和 `AGENTS.md` 当前索引。过期文档标记 `superseded` 或移入归档。

### 阶段 9：沉淀规则

若问题可能再次发生，AI 起草一条规则，说明触发条件、适用范围、必须动作、禁止动作和验证方法；经人确认后加入 `docs/rules/`。

### 阶段 10：用户视角反馈

使用 `COMPLETION_REPORT.md` 输出功能说明。技术证据保存在任务文档，主反馈不把项目负责人淹没在实现细节里。

## 八、Git 策略

- 每个任务有稳定任务 ID；
- 分支建议：`task/<任务ID>-<简述>`、`bug/<任务ID>-<简述>`、`refactor/<任务ID>-<简述>`；
- Commit 建议：`[任务ID] <完成的功能或验证检查点>`；
- 小任务可以一任务一 Commit；
- 大任务按经过验证的稳定检查点拆分多个 Commit；
- 测试与对应功能修改进入同一证据链；
- 共享历史优先使用 `git revert`；
- 未经明确授权不得使用会覆盖未提交修改的回退方式；
- AI 不得把“重新手动改回去”当作可靠回滚。

项目在 `AGENTS.md` 中明确 Git 权限：禁止提交、允许已验证检查点提交，或每次提交前询问。

## 九、测试策略

- 行为变化必须新增或更新自动化测试；
- Bug 修复优先先固化失败复现，再修到通过；
- 测试必须可以重复执行并进入仓库；
- 没有测试体系时，先登记缺口并建立测试基础设施任务，不能假装测试存在；
- 暂时无法自动化时，记录原因、确定性人工步骤、证据和后续自动化计划；
- 不得仅凭 AI 的文字声明任务已验证。

## 十、文档防腐

所有过程文档包含：

```yaml
---
id: TASK-YYYYMMDD-NNN
status: draft | active | completed | superseded | archived
created: YYYY-MM-DD
updated: YYYY-MM-DD
source_of_truth: true | false
supersedes:
superseded_by:
related_commits:
---
```

同一事实只在一个权威文档完整描述，其他地方只链接。`AGENTS.md` 只保留当前任务、当前规则、当前架构和少量仍会影响工作的历史记录；全量历史登记在 `docs/INDEX.md`。

文件命名：

```text
YYYYMMDD-HHMM-类型-简述.md
```

例如：

```text
20260829-1430-task-user-login.md
20260829-1615-bug-token-refresh-loop.md
20260830-0900-refactor-auth-boundary.md
```

## 十一、依赖与密钥治理

- 未经批准不得引入新依赖；
- 必须说明现有方案为何不足、包版本、许可证、维护状态和安全影响；
- 必须更新并审查锁文件；
- API Key、Token、密码、私钥、OAuth 凭据不得进入代码、测试数据、日志、文档、聊天和 Git 历史；
- 发现疑似密钥时立即停止，不复述其内容；
- 使用占位符只表达变量名称，不写真实值。

## 十二、对项目负责人的完成反馈

默认格式：

```text
功能名称：
这个功能是什么：
满足了什么需求：
终端用户怎样使用：
页面或行为发生了什么变化：
最终给用户带来了什么：
怎样确认功能已经可用：
仍需注意什么：
```

如项目没有页面，就描述命令、自动流程、通知、数据结果或用户可观察行为。

技术附录只有在以下情况提供：

- 项目负责人主动询问；
- 存在必须由其决策的技术风险；
- 验证失败或任务未完成；
- 需要其执行技术操作。

即使提供技术附录，也必须放在用户功能说明之后。

## 十三、新项目启用

1. 复制 `templates/AGENTS.md` 到项目根目录；
2. 按推荐结构创建 `docs/`；
3. 复制 `rules/` 内容到项目的 `docs/rules/`；
4. 根据真实代码填写 `PROJECT.md`、`ARCHITECTURE.md`、`MODULE_MAP.md`、`GLOSSARY.md` 和测试现状；
5. 按所用工具复制 `adapters/` 中的入口文件；
6. 在 `AGENTS.md` 中填写 Git 权限、测试命令和索引裁剪阈值；
7. 日常默认使用 `TASK_LITE.md`，只有高风险任务使用完整模板；
8. 每次完成都使用终端用户视角反馈成果。

## 十四、最终目标

- AI 换会话、换模型或换工具后仍能恢复项目认知；
- 人在写代码前发现理解和方向偏差；
- 功能、测试、文档和 Git 历史相互可追溯；
- 文档与规则不会无限膨胀和过期污染；
- 项目规模增长后仍能快速定位、维护和重构；
- 项目负责人不需要先成为专业程序员，仍能理解功能、检查方向并准确表达需求；
- AI 承担技术执行和文档劳动，人始终掌握用户价值、架构方向和最终判断。
