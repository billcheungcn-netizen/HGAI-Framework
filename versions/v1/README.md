# AI 大型软件开发控制法

> 依据 `vibecoding.mp4` 中作者的实践方法提炼。目标不是让 AI 一次性生成 Demo，而是让人能够长期操控 AI 开发、维护和重构大型软件。

## 一、方法的核心

这套方法把开发分成两个角色：

- **人负责控制**：确定目标、架构、边界、优先级和验收标准，检查 AI 有没有理解错、找错模块或破坏结构。
- **AI 负责执行**：检索资料、制定计划、编写代码、生成文档、修复问题、执行验证和完成大规模重构。

AI 的主要问题不是不会生成代码，而是在项目变大以后容易丢失历史、误解需求、找错位置、局部打补丁和持续消耗 Token。解决办法不是只换更强的模型，而是建立一个可持续的控制系统：

```text
外部记忆 → 文档索引 → 精确定位 → 计划审查 → 受控执行
        → 验证结果 → 更新记忆 → 架构审计 → 必要时重构
```

## 二、七条基本原则

### 1. 把项目记忆外部化

不能依赖某次对话的上下文。每个需求、Bug、开发计划、关键判断、执行过程和结果都要写入项目文档。

文档首先是 AI 的长期记忆，同时也必须让人能够读懂和审查。

### 2. 先查索引，再读文档和代码

项目根目录必须有一个简洁的 `AGENTS.md`，作为整个项目的总入口。它记录：

- 项目目标和硬性规则；
- 模块职责和依赖方向；
- 重要文档的用途和位置；
- 当前任务、历史任务、Bug 和重构记录的入口；
- AI 每次工作必须遵守的流程。

AI 不应默认扫描整个仓库。正确顺序是：

1. 阅读 `AGENTS.md`；
2. 根据索引找到相关文档；
3. 根据模块地图定位目录；
4. 只读取与任务有关的文件；
5. 有证据表明范围不足时再扩大检索。

### 3. 先形成书面计划，再修改代码

任何需求和 Bug 修复都先建立任务文档。计划至少要明确：

- AI 对需求的理解；
- 目标模块和目标文件；
- 不允许修改的范围；
- 准备怎样实现；
- 是否会改变模块依赖；
- 如何验证结果；
- 可能的风险和未知项。

计划的作用是把 AI 的内部理解暴露出来，让人能在写代码之前发现方向错误。

### 4. 人重点审查方向，不必逐行代替 AI

人优先检查：

- 需求是否理解正确；
- 找到的目录、文件和模块是否正确；
- 是否违反既有架构；
- 是否把问题推给了兜底、兼容或重复逻辑；
- 验收标准是否足以证明任务完成。

正常模式下，人确认计划后再让 AI 执行。精力不足或任务风险很低时，可以不逐项审核，但计划和执行记录仍必须保留，方便之后恢复现场和追查问题。

### 5. 架构优先于功能数量

长期项目必须持续强调：

- 模块化；
- 单向依赖；
- 高内聚、低耦合；
- 明确的业务边界；
- 展示层不侵入业务层；
- 一个职责只保留一个权威实现；
- 未经批准不得用兜底、兼容分支或复制逻辑掩盖结构问题。

这些限制要像负面提示词一样，在 `AGENTS.md`、任务文档和开发提示中反复出现。不能假设模型已经记住。

### 6. 把重构当作日常开发的一部分

AI 很容易通过局部修改快速满足当前需求，同时逐渐破坏整体结构。因此不能等项目完全失控后才重构。

出现以下信号时，应暂停增加功能并进入重构：

- 同一业务逻辑出现在多个位置；
- 模块之间出现反向或循环依赖；
- 为了修一个问题不断增加兜底分支；
- AI 多次找错模块；
- 一个小需求需要读取大量无关代码；
- 文件职责无法用一句话解释；
- 文档描述与代码现实不一致；
- 新需求越来越难精确指定到目录或文件。

AI 降低了机械重构的执行成本，人应把节省下来的成本用于更频繁地整理架构。

### 7. 把 Token 当作需要管理的开发资源

模糊地说“帮我实现这个功能”，会迫使 AI 扫描更多代码并进行更长推理。

降低 Token 消耗的主要方式不是缩短一句提示词，而是提高定位精度：

- 用 `AGENTS.md` 快速找到相关文档；
- 用模块地图快速找到责任模块；
- 尽量指定目录、文件、接口或调用链；
- 只带与当前任务有关的上下文；
- 把已经确认的结论写入文档，避免反复重新推理；
- 任务完成后更新索引，让下一次检索更短。

## 三、推荐的项目结构

```text
项目根目录/
├─ AGENTS.md                   # AI 每次工作的第一入口
├─ docs/
│  ├─ system/
│  │  ├─ PROJECT.md            # 项目目标、用户和核心能力
│  │  ├─ ARCHITECTURE.md       # 架构、分层和依赖方向
│  │  ├─ MODULE_MAP.md         # 模块职责、目录和主要入口
│  │  └─ GLOSSARY.md           # 业务术语和名称约定
│  ├─ tasks/
│  │  ├─ active/               # 正在执行的需求
│  │  └─ completed/            # 已完成需求及执行记录
│  ├─ bugs/
│  │  ├─ active/
│  │  └─ completed/
│  ├─ refactors/               # 架构问题和重构记录
│  ├─ decisions/               # 重要架构与业务决策
│  ├─ audits/                  # 定期架构、文档和代码审计
│  └─ handoffs/                # 暂停、跨会话和次日恢复记录
└─ 源代码目录/
```

`AGENTS.md` 保持简洁，只存放规则、地图和索引。详细过程放入 `docs/`，避免每个任务都携带全部历史。

## 四、完整开发闭环

### 阶段 0：恢复项目认知

AI 必须先阅读：

1. `AGENTS.md`；
2. 项目架构和模块地图；
3. 与当前任务直接相关的历史文档；
4. 当前任务涉及的代码。

输出当前理解、目标模块、已知限制和仍需确认的问题。

### 阶段 1：定位任务

明确：

- 需求属于哪个业务域；
- 责任模块在哪里；
- 现有实现和调用入口在哪里；
- 是否存在历史任务、Bug 或决策记录；
- 哪些文件不应被修改。

如果不能精确定位，不要立即编码，先补充检索或更新模块地图。

### 阶段 2：形成开发计划

使用 `templates/TASK.md` 或 `templates/BUG.md` 建立文档，记录目标、范围、步骤、架构约束和验证方法。

计划必须具体到模块和文件级别。若只能写成“搜索相关代码后修改”，说明项目认知仍然不足。

### 阶段 3：人工检查门

人快速检查：

- 理解有没有偏差；
- 模块有没有选错；
- 有没有改变不该改变的依赖；
- 有没有试图增加兜底、兼容或重复实现；
- 验证方案是否覆盖真实需求。

发现偏差时先改计划，不要让错误计划进入代码。

### 阶段 4：受控执行

AI 按批准后的计划执行，并遵守：

- 不擅自扩大范围；
- 不顺手修改无关模块；
- 不用临时补丁隐藏根因；
- 不创建第二套平行实现；
- 如实际代码与计划不一致，暂停并更新计划；
- 每个重要判断都写入任务文档。

### 阶段 5：验证

至少检查：

- 功能是否符合验收标准；
- 原问题能否稳定复现并确认消失；
- 相关测试、构建、类型检查是否通过；
- 是否修改了错误模块；
- 是否出现新依赖、重复逻辑或兼容分支；
- 文档与最终代码是否一致。

验证失败时，先记录事实和根因，再开始下一轮修改。

### 阶段 6：更新项目记忆

任务结束后：

1. 补全实际修改文件和验证结果；
2. 记录与原计划的差异；
3. 更新模块地图或架构文档；
4. 将任务移入 completed；
5. 在 `AGENTS.md` 中增加或更新索引；
6. 如果仍有未完成事项，写入 handoff 文档。

### 阶段 7：检查是否需要重构

不要只问“功能是否能用”，还要问：

- 下次修改能否快速定位？
- 模块职责是否比修改前更清晰？
- 依赖方向是否保持单向？
- 是否增加了未来必须偿还的临时逻辑？
- AI 下一次是否需要读取更多代码才能理解这里？

若答案变差，应立即建立重构任务。

## 五、三种工作模式

### 严格模式

适用于新架构、核心业务、跨模块修改和高风险 Bug。

```text
索引 → 检索 → 书面计划 → 人工批准 → 执行 → 完整验证 → 更新文档
```

### 快速模式

适用于范围明确、低风险、可快速验证的修改。

```text
索引 → 简短书面计划 → 执行 → 验证 → 更新记录
```

可以省略等待批准，但不能省略计划和结果记录。

### 重构模式

适用于项目开始混乱、AI频繁跑偏或 Token 明显上升时。

```text
架构审计 → 列出边界问题 → 确定目标结构 → 分模块重构
        → 每步验证 → 更新模块地图 → 删除旧实现
```

重构不能变成“再增加一层兼容”。目标是减少实现、依赖和认知路径。

## 六、新项目启用步骤

1. 将 `templates/AGENTS.md` 复制到项目根目录并填写。
2. 创建推荐的 `docs/` 目录。
3. 先写 `PROJECT.md`、`ARCHITECTURE.md` 和 `MODULE_MAP.md`。
4. 把当前真实代码和模块入口登记到 `AGENTS.md`。
5. 以后所有需求使用 `TASK.md`，所有 Bug 使用 `BUG.md`。
6. 每次工作结束生成一份执行记录或 handoff。
7. 定期使用 `ARCHITECTURE_AUDIT.md`，发现漂移就安排重构。
8. 把 `PROMPTS.md` 中的提示复制给所使用的 AI 开发工具。

## 七、这套方法的最终目标

不是让 AI “一次写对”，而是让项目具备以下能力：

- AI 换模型或换会话后仍能迅速恢复项目认知；
- 人能在编码前发现 AI 的理解偏差；
- Bug 和需求能定位到明确模块；
- 每次修改都有计划、结果和证据；
- 项目规模增长后仍能持续维护；
- Token 消耗随定位能力提高而下降，而不是随代码量无限增长；
- AI 承担大量执行劳动，人始终掌握架构和方向。
