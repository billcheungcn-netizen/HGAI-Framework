# HGAI Framework Skill
# @怡宝 Bill Cheung
> **Human-Governed AI Software Development Framework**
>
> 中文名称：AI 大型软件开发控制法 V2.1

HGAI 不是一个独立的软件页面，也不是“一句话生成软件”的提示词。它是一套嵌入现有项目的 AI 开发控制方法：人决定真实需求、产品方向和高影响授权；AI 负责计划、开发、测试和技术复核；Git、测试与 CI 负责提供可以核对的证据。

一句话概括：

> **用户仍然通过 Codex、Claude Code 或 Cursor 用自然语言提出需求；HGAI 负责让 AI 按“先理解、再计划、经确认后实施、测试、审核、验收”的流程工作。**

## 一、HGAI 的工作方式

HGAI 更像安装在项目里的“开发工作规程、项目记忆和验收机制”，而不是一个需要用户登录操作的新后台。

它主要解决以下问题：

- AI 换会话后忘记以前做过什么；
- 项目变大后找错模块或修改错误文件；
- AI 擅自扩大范围，增加兜底、兼容或重复实现；
- 多个 AI 同时修改相同模块，互相覆盖；
- 功能、测试、文档和 Git 历史相互脱节；
- AI 只说“已经完成”，却没有真实验证证据；
- 把“本地写完”误报成“已经合并或发布”；
- 技术修改很多，但项目负责人看不懂用户到底获得了什么。

HGAI 把一次开发任务组织成下面的闭环：

```text
用户提出需求
→ AI 用终端用户语言复述需求
→ 建立任务并确认修改范围
→ 用户确认功能方向和风险
→ AI 实现功能并同时补充测试
→ 执行用户行为验证和统一机器检查
→ 形成可追溯的 Git 检查点
→ 第二个 AI 对固定版本进行只读审核
→ 作者根据问题修改并接受复审
→ 更新项目记忆和规则
→ 用户按真实页面或行为验收
→ 用户决定是否合并和发布
```

## 二、页面、功能和交互方式

### 1. HGAI 本身没有独立业务页面

用户不需要进入一个叫“HGAI 控制台”的页面。日常入口仍然是正在使用的 AI 开发工具，例如：

- Codex；
- Claude Code；
- Cursor。

最终用户也仍然在原有产品的页面、客户端、命令或业务流程里使用新功能。HGAI 位于用户需求和实际开发之间，控制 AI 怎样理解、实施、验证和汇报。

### 2. 用户能够感知的三层交互

#### 用户交互层

用户直接用自然语言告诉 AI：现在遇到什么问题，希望用户最终能够做什么。

#### 计划确认层

AI 在修改前先说明：

- 要做成什么功能；
- 用户从哪里进入；
- 用户怎样操作；
- 页面、状态或流程会发生什么变化；
- 本次明确不做什么；
- 有哪些风险和需要授权的动作；
- 用户最后怎样验收。

用户主要检查这些内容，不需要审核函数、接口或代码结构。

#### 后台控制层

HGAI 要求 AI 在项目内部维护任务计划、责任范围、测试证据、版本检查点、审核记录和交接信息。这些工作主要由 AI 自动完成，项目负责人只在需要判断方向、风险或授权时介入。

### 3. 三种工作模式

#### 快速模式

默认用于范围明确、风险较低、可以快速验证的任务，例如文字、样式、小交互和局部修复。

#### 严格模式

用于登录、权限、支付、数据迁移、跨模块修改、公共基础能力和其他高风险任务。严格模式会增加完整计划、独立工作区、机器门禁、固定 Commit 和第二 AI 只读审核。

#### 重构模式

用于项目结构混乱、AI 经常找错位置、重复实现增加、文档失真或维护成本明显上升的情况。目标不是增加包装层，而是恢复清晰的模块边界和可维护性。

模式越严格，前期确认和验证步骤越多，但对现有用户、数据和长期维护越安全。

## 三、用户如何操作 HGAI

### 1. 首次接入项目

用户可以直接告诉 AI：

```text
为当前项目接入 HGAI Framework。
先盘点项目提供给终端用户的功能、真实代码、测试和 Git 状态，
不要修改业务功能。
```

AI 会根据真实项目建立项目说明、模块地图、统一术语、任务记录、规则入口和验证方法。不确定的内容必须标记为待确认，不能根据项目名称猜测。

如果已经安装 HGAI 个人技能，也可以使用：

```text
Codex：$hgai-framework 为当前项目接入 HGAI
Claude Code：/hgai-framework 为当前项目接入 HGAI
```

个人技能只负责让 AI 认识并正确调用 HGAI。每个真实项目仍然需要根据自己的代码、用户流程和测试能力完成一次项目级初始化。

### 2. 日常提出需求

小范围需求可以这样说：

```text
按照 HGAI 快速模式处理下面的需求：

在订单详情页增加“复制订单号”功能。
用户点击后，应复制完整订单号，并看到明确的成功提示。
```

高风险需求可以这样说：

```text
按照 HGAI 严格模式处理这个需求。
先给我看用户功能、页面变化、用户收益、风险和验收方法，
未经我确认不要开始修改。
```

### 3. 用户确认计划

AI 应当先给出类似下面的说明：

> 订单详情页会增加一个复制入口。用户点击后，系统会把当前订单号写入剪贴板，并提示“订单号已复制”。本次只修改订单详情功能，不改变订单数据、支付流程或发货状态。

用户确认的是：这是不是自己真正需要的功能，入口和操作是否合理，有没有改动不该改的内容。

### 4. 对高影响动作单独授权

提到 HGAI 不代表 AI 自动获得所有权限。下面这些动作仍然需要用户分别授权：

- 引入新的第三方依赖或付费服务；
- 读取或迁移真实数据；
- 修改权限或安全边界；
- 创建 Git Commit；
- 推送到远端；
- 合并分支；
- 部署或正式发布。

### 5. 按真实用户操作验收

任务完成后，用户按照实际页面、按钮、提示、状态或业务流程进行验收，而不是只看 AI 给出的代码清单。

## 四、HGAI 如何实现用户需求

HGAI 不代替 Codex、Claude Code 或 Cursor 编写代码。它控制这些 AI 完成需求的全过程：

1. 把用户原话转换成明确的功能、使用方法和验收标准；
2. 读取项目入口、规则、模块地图和相关历史；
3. 找到真正负责这个功能的模块，声明允许和禁止修改的范围；
4. 在修改前暴露页面变化、风险、非目标和验证方法；
5. 获得用户确认后，由作者 AI 实现功能并同步完成自动化测试；
6. 先验证真实用户行为，再执行项目统一的测试、构建和检查；
7. 在获得授权后形成可以回退的 Git 检查点；
8. 高风险任务由第二个 AI 对固定版本进行只读复核；
9. 发现问题时退回作者修改，再对新版本复审；
10. 更新项目记忆，让下一次会话或另一个 AI 能继续工作；
11. 用终端用户语言说明功能、使用方法、可见变化、收益和注意事项。

HGAI 要求下面的状态始终分开报告：

```text
功能实现：完成或未完成
本地验证：通过、失败或未运行
远端 CI：通过、失败或未运行
独立审核：通过、修改后复审、阻止或未进行
已合并主分支：是或否
已发布给用户：是或否
```

这样项目负责人不会把“本地已经写完”误解为“用户现在已经可以使用”。

## 五、HGAI 如何协同两个 AI

HGAI 协同两个 AI 的核心不是让它们同时写同一份代码，而是把它们分成两个独立角色：

> **AI-A 负责施工，AI-B 负责验收；项目文档和 Git 负责传递事实，人负责方向和最终授权。**

```text
用户提出需求
    ↓
AI-A：计划、实施、测试、记录
    ↓
形成固定的 Git 检查点
    ↓
AI-B：针对这个检查点只读审核
    ↓
通过 ─────────→ 用户验收
有问题 → AI-A 修改 → 新检查点 → AI-B 复审
```

### 1. AI-A：作者 AI

作者 AI 负责：

- 理解和复述用户需求；
- 建立任务并认领修改范围；
- 制定功能、页面变化和验收计划；
- 编写功能和自动化测试；
- 执行本地验证并记录真实结果；
- 在获得授权后形成 Git 检查点；
- 根据审核意见完成修订。

作者可以是 Codex、Claude Code 或 Cursor。

### 2. AI-B：审核 AI

审核 AI 默认只读，负责检查：

- 用户功能是否符合原始需求；
- 是否修改了不应该修改的功能；
- 页面是否可能错误显示成功；
- 异常是否被吞掉或被兜底掩盖；
- 权限、数据和安全边界是否正确；
- 测试是否真正覆盖用户操作；
- 作者提供的验证证据是否与目标版本一致；
- 完成报告是否把本地完成夸大成已经发布。

审核结论使用以下三种状态：

- **通过**：没有发现阻止交付的问题；
- **修改后复审**：作者修正问题后，需要审核新版本；
- **阻止**：存在严重风险，当前版本不能继续交付。

审核 AI 发现问题后不顺手修改作者代码，而是把问题退回作者。这样不会出现“自己写、自己改、最后自己证明正确”的情况。

### 3. 两个 AI 靠什么交接

两个 AI 不依赖彼此的聊天记忆，而是共用项目中的事实：

- 同一份项目说明和规则；
- 同一个任务 ID；
- 同一份任务计划；
- 同一个待审核 Commit；
- 同一份测试和 CI 证据；
- 同一份审核与交接记录。

审核时不能只说：

```text
帮我审核刚才改的代码。
```

应当明确说：

```text
只读审核任务 TASK-... 对应的 Commit abc123...。
```

这样即使作者继续修改，审核者检查的对象也不会悄悄改变。

一次完整交接至少要说明：

- 任务 ID；
- 当前 Commit；
- 已完成的用户功能；
- 尚未完成的部分；
- 实际运行过的验证；
- CI 结果；
- 当前风险；
- 下一步允许做什么。

### 4. 发现问题后的复审循环

以“取消订单”功能为例：

1. AI-A 完成功能和测试，形成 Commit A；
2. AI-B 只读审核 Commit A；
3. AI-B 发现“已发货订单也能取消”，结论为“修改后复审”；
4. AI-B 只说明用户风险和修改要求，不直接修改；
5. AI-A 修复问题，重新验证并形成 Commit B；
6. AI-B 审核 Commit B；
7. 问题关闭后，审核结论变为“通过”；
8. 用户再决定是否合并和发布。

如果审核发现需求本身存在冲突，或者需要扩大范围、迁移数据、增加费用或改变安全边界，两个 AI 都不能替用户作决定，必须暂停并请求用户判断。

### 5. 两个 AI 是否可以并行

可以，但必须区分情况：

- **同一个任务**：只能有一个写入者，另一个 AI 只读审核；
- **不同任务**：可以分别在独立分支或独立工作区施工，但必须登记各自负责的模块和文件；
- **范围发生重叠**：后开始的任务暂停，由项目负责人决定合并、排序或重新划分范围。

HGAI 的并行不是简单地让更多 AI 同时动手，而是让每个 AI 都拥有清楚、互不冲突的责任边界。

### 6. 推荐组合

- Codex 负责实施，Claude Code 对指定 Commit 只读审核；
- Claude Code 负责实施，Codex 对指定 Commit 只读审核；
- Cursor 负责前端页面和交互实现，Codex 或 Claude Code 审核业务边界、测试和回归风险；
- 同一个 AI 的内置 Review 可以作为第一遍检查，另一个独立 AI 作为严格任务的最终技术审核者。

HGAI 当前提供的是协作协议和项目内的事实记录，不是一个自动调度两个 AI 的在线平台。通常仍由用户或外层开发工具启动第二个 AI 的审核任务；但第二个 AI 可以通过任务和 Git 记录准确恢复上下文，不需要用户重新讲完整个项目。

## 六、用户在双 AI 协作中做什么

项目负责人不需要充当两个 AI 之间的技术翻译，主要负责：

1. 说明真实用户问题和期望结果；
2. 确认功能、入口、操作方式、页面变化和非目标；
3. 指定或接受谁负责实施、谁负责审核；
4. 对数据迁移、依赖、推送、合并和发布等高影响动作授权；
5. 当两个 AI 对产品方向存在分歧时作出业务决定；
6. 根据最终用户操作完成验收。

技术架构、代码实现、测试完整性和依赖方向，可以交给作者 AI 与审核 AI 分工处理。

## 七、最终给用户带来的效果

采用 HGAI 后，用户获得的不是一个额外页面，而是一种更可控的 AI 开发体验：

- AI 更少误解需求、改错功能或擅自扩大范围；
- 用户能在写代码前发现方向偏差；
- 功能是否测试、审核、合并和发布更加清楚；
- 多个 AI 可以接力或交叉审核，不依赖某一个聊天窗口的记忆；
- 项目变大后仍然容易定位、维护和重构；
- 非专业程序员也能掌握产品方向、风险授权和最终验收；
- 功能、测试、文档和 Git 历史形成可追溯的证据链；
- 出现问题时能够回到明确检查点，而不是让 AI 凭记忆“改回来”。

严格模式的代价是前期会增加计划、确认、验证和复核步骤，因此不像“一句话立即生成”那么快。换来的结果是需求更清楚、修改更可控、证据更真实、长期维护更稳定。

HGAI 不能保证软件永远没有缺陷，也不能替代人的产品判断、真实测试和发布授权。它的价值在于：让错误更早暴露，让责任更清楚，让每个“已经完成”都有相应证据。

## 八、核心结论

HGAI 最终建立的是下面的责任关系：

- 人提出真实用户需求、确认用户结果并授权高影响动作；
- 作者 AI 负责计划、实现、测试、记录和修订；
- 第二个 AI 负责对固定版本进行只读技术复核；
- Git、测试、扫描和 CI 负责提供机器证据；
- 项目文档负责跨会话、跨模型和跨工具保存项目认知；
- 所有面向项目负责人的主要反馈，都先说明终端用户获得了什么、怎样使用、页面或行为发生了什么变化，以及最终带来了什么结果。
