# HGAI Framework

> **Human-Governed AI Software Development Framework**
>
> 中文名称：AI 大型软件开发控制法 V2.1

依据 `0.07 ebN:/ A@T.YM 09/07 :5pm 聊聊大项目的vibecoding # vibecoding # ai新星计划 # vibecoding大赏  https://v.douyin.com/Z1bA4DXiykU/ 复制此链接，打开Dou音搜索，直接观看视频！` 中作者的实践方法提炼，并经过两轮交叉审核升级。同时加入非专业程序员协作原则，有效提升非专业程序员利用AI开发软件的沟通效率。人决定用户需求、方向和授权；AI 负责开发与审核；工具负责提供验证证据。 V1、V2 分别保存在 `versions/v1/`、`versions/v2/`。

## 一、这套控制法解决什么

这不是“一句话生成软件”的提示词，而是一套让人长期操控 AI 开发、维护和重构软件的方法。

它解决九类常见失控：

- AI 忘记以前做过什么；
- 项目变大后找错模块或修改错误文件；
- 用兜底、兼容和重复实现快速糊住问题；
- 文档、代码、测试和 Git 历史相互脱节；
- 文档越积越多，最后反过来成为幻觉源；
- 模糊检索导致 Token 和开发成本持续上升；
- AI 完成了技术修改，却无法用项目负责人和终端用户能理解的语言说明成果。
- AI 声称已经验证，但没有机器执行和远端 CI 证据；
- 多个 AI 同时开发时任务撞号、重复劳动或修改相同模块。

完整闭环：

```text
恢复项目认知
→ 生成唯一任务 ID 并认领写入范围
→ 索引并精确定位
→ 书面计划
→ 人检查方向
→ 建立可回退基线
→ 受控执行并同步产出测试
→ 验证用户行为和技术结果
→ 提交可追溯 Git 检查点
→ 远端 CI 证明并由第二 AI 只读复核
→ 更新唯一权威文档与规则
→ 用终端用户语言反馈成果
→ 审计架构并持续重构
```

## 二、角色分工

### 人负责

- 说明真正要解决的用户问题；
- 确认 AI 是否理解了需求；
- 判断功能是否真的满足项目负责人或终端用户；
- 决定产品方向和非目标；
- 授权第三方依赖、数据迁移、远端推送、发布等高影响动作。

人不需要是专业程序员，也不应被迫阅读大量代码和术语才能判断任务是否完成。

### AI 负责

- 读取索引、历史文档、规则和代码；
- 自动填写任务、Bug、测试和交接文档；
- 提出文件级计划；
- 编写代码和自动化测试；
- 执行验证并记录真实证据；
- 维护索引、模块地图、术语表和规则库；
- 把技术修改翻译成终端用户能够理解的功能变化。
- 不同 AI 在严格模式下分别承担作者和只读技术审核者；
- 每个技术审核结论附一条非程序员也能理解的用户影响说明。

### 工具负责

- Git 记录可回退检查点；
- 测试、构建、类型检查和静态检查提供可重复证据；
- CI、锁文件和密钥扫描提供持续约束。
- 远端 CI 把验证结果绑定到具体 Commit，并在适用时阻止未通过的代码合并。

## 三、九条核心原则

### 1. 外挂记忆

每个需求、Bug、开发计划、关键判断、执行结果和教训都写入项目文档。不能依赖某次对话仍然存在。

### 2. 索引先行

项目根目录的 `AGENTS.md` 是 AI 的第一入口。AI 必须先通过索引找到相关文档、规则、模块和代码，不得默认扫描全仓。

### 3. 计划先于编码

任何任务先形成书面计划，把需求理解、目标模块、目标文件、禁止范围、用户行为和验证方法暴露出来，再开始修改。

### 4. 架构负面约束

持续强调模块化、单向依赖、高内聚低耦合、业务边界、禁止未经批准的兜底和兼容、禁止重复实现。不能假设模型已经记住这些要求。

### 5. 测试与功能同批交付

功能变化必须新增或更新自动化测试。Bug 修复优先先形成可失败的复现测试，再修到通过。测试代码与功能代码属于同一任务、同一证据链。

### 6. Git 是真实的代码证据链

任务文档、代码修改、测试结果和 Git Commit 必须通过任务 ID 相互关联。高风险重构在独立分支和已验证基线上进行，跑偏时恢复到干净检查点，不让 AI 凭记忆“改回来”。

### 7. 文档和规则必须防腐

同一事实只有一个权威来源。所有文档有状态、更新时间、替代关系和关联 Commit。主索引只保留当前有效内容，过期内容进入归档，不能让 `AGENTS.md` 无限增长。

### 8. 面向项目负责人的沟通必须使用终端用户语言

内部过程可以包含文件、模块、接口、测试和代码；对项目负责人的主反馈默认必须说明：

1. 做成了什么功能；
2. 这个功能是什么；
3. 满足了项目负责人或终端用户什么需求；
4. 用户如何使用；
5. 页面、状态或操作流程发生了什么变化；
6. 最终给用户带来了什么结果；
7. 怎样用用户能够理解的方式验证。

除非对方主动要求技术细节，否则不得在主反馈中堆专业术语、代码片段、文件清单或实现过程。不能假设项目负责人本身是专业程序员。

### 9. Token 和检索成本必须主动管理

定位顺序为：`指定文件 → 指定模块 → 终端用户现象 → 受限范围搜索 → 全仓搜索`。从左到右 Token、时间和误判成本逐级增加。

AI 必须从最精确层开始，只有证据表明范围不足时才能扩大一级。任务结束后若定位成本过高，应更新模块地图、术语表或索引；如果问题来自架构混乱，应建立重构任务。

## 五、文档字段责任

模板统一使用以下标记：

- **`[AI填写]`**：AI 根据真实项目自动生成，人不必手写；
- **`[人审-用户]`**：人只从项目负责人或终端用户角度确认功能、需求、使用方式、可见变化和用户收益；
- **`[人授权]`**：人决定引入依赖、迁移数据、推送远端、合并、发布及其他高影响动作；
- **`[AI交叉审-技术]`**：第二个 AI 只读检查责任模块、依赖方向、测试、架构、安全和回退方案；
- **`[工具证明]`**：由测试、构建、CI、扫描和 Git 真实产生，不能凭空填写；
- **`[自动维护]`**：任务结束时由 AI 更新索引、模块地图、术语表、规则和交接文档。

原则是：**文档由 AI 写，人判断用户价值并授权高影响动作；技术正确性由另一个 AI 复核，由工具提供证据。** 每个技术审核结论还要附一句用户语言摘要，让非程序员能理解它对功能和风险的影响。

## 六、三种工作模式

### 快速模式：默认

适用于范围明确、低风险、可快速验证的修改，使用 `TASK_LITE.md`。

```text
检查任务占用并认领 → 索引 → 轻量计划 → 人审用户结果
→ 代码与测试 → 本地统一验证 → Git 检查点（如获授权）
→ 远端 CI（如项目已建立）→ 按风险交叉审核
→ 更新索引 → 分状态的用户视角反馈
```

### 严格模式

适用于新模块、核心业务、跨模块修改、数据迁移、安全事项和高风险 Bug，使用完整 `TASK.md`。

```text
恢复认知 → 唯一 ID 与任务认领 → 深入定位 → 完整计划
→ 人审用户结果并授权高影响动作 → 独立分支或工作树
→ 分检查点执行和自动化测试 → 本地机器门禁 → 远端 CI
→ 第二 AI 只读技术审核 → 文档与 Git 关联 → 用户视角反馈
```

### 重构模式

适用于 AI 多次找错模块、依赖混乱、兜底增加、文档腐化或 Token 明显上升。

```text
认领写入范围 → 建立已验证基线 → 独立重构分支或工作树 → 架构审计
→ 目标结构 → 分步重构和测试 → 每步提交
→ 机器门禁与远端 CI → 第二 AI 只读技术审核
→ 删除旧实现 → 更新模块地图和规则 → 用户影响说明
```

## 七、标准任务闭环

### 阶段 0：恢复项目认知

AI 阅读 `AGENTS.md`、当前有效规则、项目架构、模块地图、术语表和相关历史文档。

### 阶段 1：生成唯一任务 ID 并认领

按 `TYPE-YYYYMMDD-HHMMSS-AGENT-XXXX` 生成 ID，检查 `docs/coordination/ACTIVE_TASKS.md`，登记负责人、状态、目标模块、预计写入文件和分支或工作树。与其他活动任务的写入范围重叠时必须暂停协调，不能同时动手。

### 阶段 2：用用户语言确认需求

先说明终端用户现在遇到什么问题、期望拥有什么功能、怎样使用以及成功后看见什么。业务术语先查 `GLOSSARY.md`，不允许自行猜测。

### 阶段 3：按 Token 阶梯精确定位

严格按“指定文件 → 指定模块 → 终端用户现象 → 受限范围搜索 → 全仓搜索”逐级定位。根据 `MODULE_MAP.md` 找到责任模块、目标文件、调用入口和禁止修改范围；只有证据表明当前范围不足时才能扩大一级。不能定位时继续调查，不立即编码。

### 阶段 4：建立计划并完成分工审核

低风险任务使用 `TASK_LITE.md`，高风险任务使用 `TASK.md`。AI 自动填写；人只审用户需求、功能、使用方式、可见变化和收益，并授权高影响动作。责任模块、依赖方向、测试、安全和回退由第二 AI 在严格模式下审核。

### 阶段 5：建立 Git 基线

记录当前分支、工作区状态和基线 Commit。不得覆盖尚未提交的用户修改。高风险任务按项目授权创建任务分支。

### 阶段 6：受控执行并产出测试

代码、测试、文档同步修改。实际情况与计划不符时暂停并更新计划，不擅自扩大范围，不用兜底隐藏根因。

### 阶段 7：执行本地机器门禁

先验证终端用户行为，再运行项目规定的唯一综合验证命令，使自动化测试、构建、类型检查、静态检查、架构检查和密钥扫描按项目情况真实执行。记录命令、退出状态、时间和证据位置；AI 的文字不能替代工具结果。

### 阶段 8：Git 检查点和远端 CI

在获得授权后，把经过本地验证的代码和测试提交为一个或多个可回退检查点。Commit message 引用任务 ID，不混入无关任务。再次获得或确认远端推送授权后推送，由 CI 对该 Commit 独立验证；适用时用分支保护阻止未通过的代码合并。

### 阶段 9：第二 AI 只读技术审核

严格模式、高风险任务和项目初始化必须让第二个 AI 依据任务文档、代码差异和工具证据进行只读审核。审核者默认不得修改代码；发现问题时退回作者，避免“既写又审”掩盖偏差。

### 阶段 10：更新项目记忆

更新任务文档、模块地图、术语表、文档登记表和 `AGENTS.md` 当前索引。过期文档标记 `superseded` 或移入归档。

### 阶段 11：沉淀规则

若问题可能再次发生，AI 起草一条规则，说明触发条件、适用范围、必须动作、禁止动作和验证方法；经人确认后加入 `docs/rules/`。

### 阶段 12：用户验收与分状态反馈

使用 `COMPLETION_REPORT.md` 输出功能说明，分别报告“本地已验证、远端 CI 已通过、已合并、已发布”，没有证据的状态不得写成完成。技术证据保存在任务文档，主反馈不把项目负责人淹没在实现细节里。

## 八、Git 策略

- 每个任务使用 `TYPE-YYYYMMDD-HHMMSS-AGENT-XXXX` 唯一 ID；
- 分支建议：`task/<任务ID>-<简述>`、`bug/<任务ID>-<简述>`、`refactor/<任务ID>-<简述>`；
- Commit 建议：`[任务ID] <完成的功能或验证检查点>`；
- 小任务可以一任务一 Commit；
- 大任务按经过验证的稳定检查点拆分多个 Commit；
- 测试与对应功能修改进入同一证据链；
- 共享历史优先使用 `git revert`；
- 未经明确授权不得使用会覆盖未提交修改的回退方式；
- AI 不得把“重新手动改回去”当作可靠回滚；
- 远端仓库默认使用私有可控位置；推送前检查远端地址、可见性、待推送内容和疑似密钥；
- 未经明确授权不得新增远端、推送、改写共享历史、合并或发布；
- 获得授权后定期推送已验证检查点，避免证据链只存在于单台电脑；
- “本地已提交”不等于“远端已备份”，更不等于“已合并”或“已发布”。

项目在 `AGENTS.md` 中分别明确提交、推送、合并和发布权限，不能用一次授权替代后续所有高影响动作。

## 九、测试策略

- 行为变化必须新增或更新自动化测试；
- Bug 修复优先先固化失败复现，再修到通过；
- 测试必须可以重复执行并进入仓库；
- 没有测试体系时，先登记缺口并建立测试基础设施任务，不能假装测试存在；
- 暂时无法自动化时，记录原因、确定性人工步骤、证据和后续自动化计划；
- 项目必须建立一个统一的本地验证入口，避免每个 AI 自选一套命令；
- 提交前钩子用于尽早拦截问题，但可被跳过，只能算本机弱门禁；
- 远端 CI 必须绑定具体 Commit，作为独立于当前 AI 会话的强证据；
- 不得仅凭 AI 的文字声明、配置文件存在或“应该通过”来宣布验证成功。

## 十、机器门禁与证据等级

证据从弱到强分为：

1. AI 文字说明：只能解释，不能证明；
2. 本地综合验证：证明当前工作区在该机器上真实通过；
3. 提交前钩子：帮助拦截遗漏，但不能证明无人绕过；
4. 远端 CI：把结果绑定到具体 Commit，由独立环境执行；
5. 分支保护：在适用的托管平台上，阻止未通过 CI 或未完成审核的变更合并。

每次任务都在 `VERIFICATION_EVIDENCE.md` 或任务文档中记录真实证据。任何时候都分别报告：`本地已验证`、`CI 已通过`、`已合并`、`已发布`；后一个状态不能由前一个状态推断。

## 十一、多 AI 协作

- 开工前先查 `docs/coordination/ACTIVE_TASKS.md` 并认领任务；
- 任务登记负责人、状态、模块、预计写入文件、分支或工作树和开始时间；
- 两个活动任务的写入范围重叠时，后开始者暂停并协调；
- 并行写代码默认使用独立分支或工作树，不能让多个 AI 直接争用同一工作区；
- 作者负责实现，审核者使用 `REVIEW.md` 只读复核，默认不得顺手修改；
- 技术审核结论必须附用户语言的影响摘要；
- 真实项目初始化后，在首个高风险任务前由第二 AI 对照真实代码审核 `AGENTS.md`、模块地图、测试入口、机器门禁和活动任务表。

## 十二、文档防腐

所有过程文档包含：

```yaml
---
id: TYPE-YYYYMMDD-HHMMSS-AGENT-XXXX
status: draft | active | completed | superseded | archived
created: YYYY-MM-DD
updated: YYYY-MM-DD
source_of_truth: true | false
supersedes:
superseded_by:
related_commits:
---
```

同一事实只在一个权威文档完整描述，其他地方只链接。`AGENTS.md` 只保留当前任务、当前规则、当前架构和少量仍会影响工作的历史记录；全量历史登记在 `docs/INDEX.md`。

文件命名：

```text
TYPE-YYYYMMDD-HHMMSS-AGENT-XXXX-简述.md
```

例如：

```text
TASK-20260830-143015-CODEX-A7F2-user-login.md
BUG-20260830-161522-CLAUDE-B3D8-token-refresh-loop.md
REFACTOR-20260830-170004-CURSOR-C9E1-auth-boundary.md
```

同一秒内同一工具仍可能创建多个任务，所以结尾的四位随机码不能省略。`AGENT` 使用稳定且可识别的工具或人工代号。文档内 ID 与文件名前缀必须完全一致，不再维护两套识别符。

## 十三、依赖与密钥治理

- 未经批准不得引入新依赖；
- 必须说明现有方案为何不足、包版本、许可证、维护状态和安全影响；
- 必须更新并审查锁文件；
- API Key、Token、密码、私钥、OAuth 凭据不得进入代码、测试数据、日志、文档、聊天和 Git 历史；
- 发现疑似密钥时立即停止，不复述其内容；
- 使用占位符只表达变量名称，不写真实值。

## 十四、对项目负责人的完成反馈

默认格式：

```text
功能名称：
这个功能是什么：
满足了什么需求：
终端用户怎样使用：
页面或行为发生了什么变化：
最终给用户带来了什么：
怎样确认功能已经可用：
仍需注意什么：
```

如项目没有页面，就描述命令、自动流程、通知、数据结果或用户可观察行为。

技术附录只有在以下情况提供：

- 项目负责人主动询问；
- 存在必须由其决策的技术风险；
- 验证失败或任务未完成；
- 需要其执行技术操作。

即使提供技术附录，也必须放在用户功能说明之后。

## 十五、新项目启用

1. 复制 `templates/AGENTS.md` 到项目根目录；
2. 按推荐结构创建 `docs/`；
3. 复制 `rules/` 内容到项目的 `docs/rules/`；
4. 建立 `docs/coordination/ACTIVE_TASKS.md`、`docs/reviews/` 和统一任务 ID 规则；
5. 根据真实代码填写 `PROJECT.md`、`ARCHITECTURE.md`、`MODULE_MAP.md`、`GLOSSARY.md` 和测试现状；
6. 建立并真实运行本地综合验证命令，再配置提交前钩子和远端 CI；适用时配置分支保护；
7. 按所用工具复制 `adapters/` 中的入口文件；
8. 在 `AGENTS.md` 中分别填写提交、推送、合并、发布权限，以及验证命令和索引裁剪阈值；
9. 让第二个 AI 只读审核初始化结果，并用用户语言解释每个技术风险的实际影响；
10. 修正初始化审核发现的问题后，再开始首个高风险任务；
11. 日常默认使用 `TASK_LITE.md`，只有高风险任务使用完整模板；
12. 每次完成都使用终端用户视角反馈，并分开报告本地验证、CI、合并和发布状态。

## 十六、最终目标

- AI 换会话、换模型或换工具后仍能恢复项目认知；
- 人在写代码前发现理解和方向偏差；
- 功能、测试、文档和 Git 历史相互可追溯；
- 文档与规则不会无限膨胀和过期污染；
- 项目规模增长后仍能快速定位、维护和重构；
- 项目负责人不需要先成为专业程序员，仍能理解功能、检查方向并准确表达需求；
- 多个 AI 能并行工作而不撞号、不争用同一写入范围，并能真正交叉复核；
- 验证结果由机器和远端 CI 证明，并与合并、发布状态严格区分；
- Token 成本随项目增长仍可控制，不因无边界扫描持续上升；
- AI 承担技术执行、技术交叉审核和文档劳动，人始终掌握用户价值、高影响授权和最终判断。

## 十七、HGAI 与 Codex、Claude Code、Cursor 的完整结合方法

HGAI 的正确用法，不是为三款 AI 分别维护三套项目说明，而是：

> 用一套项目记忆和规则作为唯一事实来源，再给 Codex、Claude Code、Cursor 各装一个很薄的“入口适配器”。

这样无论换哪款 AI，它们看到的项目目标、模块边界、任务状态、测试要求和用户语言要求都是一致的。

| HGAI 层级 | 作用 | Codex | Claude Code | Cursor |
|---|---|---|---|---|
| <code>AGENTS.md</code> | 项目总入口 | 自动读取 | 由 <code>CLAUDE.md</code> 引入 | 可直接读取 |
| <code>docs/system/</code> | 项目、架构、模块、术语 | 按任务读取 | 按任务读取 | 通过 <code>@文件</code> 引用 |
| <code>docs/rules/</code> | Git、测试、安全、沟通规则 | 由入口要求读取 | 由入口要求读取 | <code>.mdc</code> 适配器要求读取 |
| <code>tasks/active/</code> | 当前任务计划 | 实施前建立 | 实施前建立 | Plan Mode 保存到这里 |
| <code>ACTIVE_TASKS.md</code> | 多 AI 任务认领 | 开工前登记 | 开工前登记 | 开工前登记 |
| 验证脚本与 CI | 机器证据 | 实际运行 | 实际运行 | 实际运行 |
| 完成报告 | 面向终端用户汇报 | 用户语言 | 用户语言 | 用户语言 |

框架现有入口：

- [HGAI 使用说明](README.md)
- [可直接复制的提示词](PROMPTS.md)
- [AGENTS.md 模板](templates/AGENTS.md)
- [Claude Code 适配器](adapters/CLAUDE.md)
- [Cursor 适配器](adapters/ai-project-control.mdc)

### 17.1 所有 AI 软件共用的工作流程

无论使用哪款 AI，都应当执行同一个闭环：

~~~text
用户提出需求
    ↓
AI 用终端用户语言复述需求
    ↓
建立任务文档并登记任务认领
    ↓
定位责任模块、影响范围和验证方法
    ↓
项目负责人确认用户方向
    ↓
AI 实现功能并同时补测试
    ↓
执行测试、检查和构建
    ↓
提交 Git，任务 ID 写入 Commit
    ↓
另一 AI 对指定 Commit 只读审核
    ↓
更新项目记忆、规则和交接文档
    ↓
用终端用户语言汇报最终结果
~~~

#### 项目负责人需要做什么

不要求项目负责人判断代码结构、函数名称或技术方案。主要审查以下内容：

- 这是不是我要的功能。
- 用户将从哪里进入这个功能。
- 页面、操作流程和最终结果是否符合预期。
- 有没有改动不应该改的功能。
- 有没有高风险操作，例如数据迁移、推送上线、删除数据或新增付费服务。
- AI 是否拿出了真实测试结果，而不只是声称“已经验证”。

技术架构、测试代码和依赖方向，可以交给第二个 AI 进行交叉审核。

### 17.2 所有项目的一次性初始化

第一次把 HGAI 接入真实项目时，建议先建立分支，例如：

~~~text
chore/hgai-bootstrap
~~~

然后从本框架复制并根据真实项目填写以下内容：

~~~text
项目根目录/
├─ AGENTS.md
├─ CLAUDE.md
├─ .cursor/
│  └─ rules/
│     └─ ai-project-control.mdc
├─ scripts/
│  └─ verify.*
├─ docs/
│  ├─ INDEX.md
│  ├─ system/
│  │  ├─ PROJECT.md
│  │  ├─ ARCHITECTURE.md
│  │  ├─ MODULE_MAP.md
│  │  ├─ GLOSSARY.md
│  │  └─ TESTING.md
│  ├─ rules/
│  ├─ coordination/
│  │  └─ ACTIVE_TASKS.md
│  ├─ tasks/
│  │  ├─ active/
│  │  └─ completed/
│  ├─ bugs/
│  ├─ reviews/
│  └─ handoffs/
└─ 项目源代码/
~~~

初始化过程按以下顺序进行：

1. 让第一个 AI 盘点项目提供给终端用户的功能，而不是先堆技术名词。
2. 根据真实代码建立项目说明、架构、模块地图、术语表和测试现状。
3. 建立统一的本地验证入口，让所有 AI 使用同一套验证命令。
4. 配置远端 CI，把验证结果绑定到具体 Commit。
5. 加入 Codex、Claude Code 和 Cursor 的工具入口。
6. 让第二个 AI 只读核对初始化结果和真实代码。
7. 项目负责人只需要确认用户功能、业务边界、风险和授权项。
8. 修正复审问题后提交 HGAI 初始化检查点。
9. 首个高风险任务开始前，再确认活动任务表、权限和机器门禁确实可用。

初始化时可以使用 [PROMPTS.md](PROMPTS.md) 中的“初始化现有项目”提示词。初始化不是让 AI 凭项目名称猜测内容；无法从代码、配置、测试和运行结果证明的事项，必须标记为待确认。

### 17.3 与 Codex 结合使用

#### 17.3.1 首次接入项目

把填写完成的 <code>AGENTS.md</code> 放在项目 Git 根目录。

~~~text
your-project/
├─ AGENTS.md
├─ docs/
│  ├─ INDEX.md
│  ├─ system/
│  ├─ rules/
│  ├─ coordination/
│  ├─ tasks/
│  │  ├─ active/
│  │  └─ completed/
│  └─ bugs/
├─ src/
└─ tests/
~~~

Codex 会从项目根目录向当前工作目录逐层读取 <code>AGENTS.md</code>；更靠近当前模块的 <code>AGENTS.md</code> 可以增加模块专属规则。因此，大型项目可以使用：

~~~text
AGENTS.md                 全项目规则
frontend/AGENTS.md        前端模块补充规则
backend/AGENTS.md         后端模块补充规则
payment/AGENTS.md         支付模块严格规则
~~~

不要把几十页项目资料全部塞进根 <code>AGENTS.md</code>。它应当保持为“索引和硬约束”，再要求 Codex 按任务读取具体文档。Codex 默认有项目指令大小限制，过长会造成后面的规则无法进入上下文。参见 [OpenAI：AGENTS.md 使用说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)。

完成后，在项目根目录对 Codex 说：

~~~text
请列出本次会话实际读取到的全部 AGENTS.md 和指令文件，
然后用终端用户语言总结当前项目的目标、模块划分、硬约束和验证要求。
暂时不要修改文件。
~~~

这样可以确认入口是否真正生效。还应检查 Codex 是否只读取了入口文件，而没有读取任务所需的规则和项目资料。<code>AGENTS.md</code> 中引用了某个文件，不等于每次会话都已经自动加载了该文件；HGAI 入口必须明确要求 Codex 在相应阶段读取相关资料。

#### 17.3.2 用 Codex 初始化现有项目

使用 HGAI 的“初始化现有项目”提示词，让 Codex 完成：

- 识别项目提供给终端用户的核心功能。
- 建立模块地图。
- 建立统一术语表。
- 记录测试、构建、启动命令。
- 标出高风险目录和禁止修改区域。
- 建立统一验证脚本。
- 建立最小 CI。
- 生成 <code>AGENTS.md</code> 和项目文档。
- 不确定的内容明确标记为待确认，不允许猜测。

初始化后不要立即让同一个 Codex 继续开发。应让 Claude Code 或 Cursor 对初始化结果做一次只读复审，重点检查模块地图是否和真实代码一致。

#### 17.3.3 Codex 快速任务模式

快速模式适合小范围、低风险修改，例如文字、样式、小交互和局部修复。

可以直接说：

~~~text
按照 HGAI 快速模式处理下面的需求：

用户需求：
在订单详情页增加“复制订单号”功能。
用户点击后，应当复制完整订单号，并看到明确的成功提示。

要求：
1. 先读取 AGENTS.md、术语表、模块地图和当前活动任务。
2. 登记任务认领，避免和其他 AI 修改同一模块。
3. 创建 TASK_LITE 任务文档。
4. 先用终端用户语言说明准备实现什么、页面会怎样变化。
5. 我确认后再修改。
6. 功能代码和自动化测试必须同时交付。
7. 实际运行项目规定的验证命令。
8. 最终不要向我堆砌代码和专业术语。
~~~

Codex 应先给出类似这样的计划：

> 订单详情页会增加一个复制入口。用户点击后，系统会把当前订单号写入剪贴板，并在页面上提示“订单号已复制”。本次只修改订单详情功能，不改变订单数据和支付流程。

这才是项目负责人需要审查的内容。

#### 17.3.4 Codex 严格任务模式

以下情况使用严格模式：

- 涉及登录、权限、支付或数据迁移。
- 跨越多个模块。
- 修改公共组件或基础架构。
- 预计超过一个工作时段。
- 可能影响已有用户数据。
- 多个 AI 同时工作。

建议为任务建立独立 Worktree。Codex 的 Worktree 会提供相互隔离的代码目录，适合并行任务。参见 [OpenAI：Codex Git Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees.md)。

但要注意：

> Worktree 中未提交的 <code>ACTIVE_TASKS.md</code> 不会自动同步给其他分支。

因此，多 AI 并行时，应当先在主控制分支登记任务认领并提交，或者使用统一的 GitHub Issue 或项目看板作为任务占用登记，之后再进入各自 Worktree。

严格任务的启动指令可以写成：

~~~text
按照 HGAI 严格模式处理该需求。

先执行：
1. 读取项目入口、规则索引、模块地图、术语表和活动任务。
2. 生成唯一任务 ID。
3. 登记责任模块和计划修改路径。
4. 创建完整 TASK 文档。
5. 给我一份只包含用户功能、页面变化、用户收益、风险和验收方式的计划。
6. 未经我确认，不得进入编码阶段。
~~~

#### 17.3.5 Codex 计划确认后的执行

项目负责人确认用户功能和风险后，对 Codex 说：

~~~text
任务计划已经确认。

请严格按照已批准的任务文档执行：
- 不扩大范围；
- 不修改未列入计划的模块；
- 如果发现计划需要改变，立即暂停并说明；
- 功能和自动化测试必须同批完成；
- 执行项目统一验证入口；
- 把真实命令、退出状态和结果写入验证证据；
- 不允许把“代码看起来正确”写成“验证通过”。
~~~

如果实际代码与计划不一致，Codex 应暂停并说明：

- 新发现了什么。
- 为什么原计划不能继续。
- 对终端用户会产生什么影响。
- 是否需要扩大责任模块。
- 需要项目负责人决定或授权什么。

#### 17.3.6 Codex 实施后的 Git 检查点

实现和本地验证完成后，在获得提交授权的前提下创建检查点：

~~~text
feat(order): TASK-20260830-153012-CODEX-A3F7 add order number copy action
~~~

提交信息必须关联任务 ID。若任务较大，可以按经过真实验证的稳定阶段拆成多个 Commit，但不能把无关任务混入同一个提交。

推送远端、合并和发布是三个独立授权动作。本地 Commit 不表示代码已经备份、合并或交付给终端用户。

#### 17.3.7 使用 Codex 审核

实现完成后，可以使用 Codex 的 <code>/review</code> 审查指定 Commit、当前改动或相对主分支的变化。该模式专门报告问题，不直接修改工作树。参见 [OpenAI：Codex Code Review](https://learn.chatgpt.com/docs/code-review.md)。

审核指令：

~~~text
只读审核 Commit <commit-id>。

请对照：
- 关联任务文档
- 用户验收标准
- 模块边界
- 测试规则
- 安全与密钥规则
- 用户语言沟通规则

重点检查：
1. 是否真正实现了用户需要的功能。
2. 是否修改了无关模块。
3. 是否遗漏异常路径和自动化测试。
4. 是否使用兜底逻辑掩盖根因。
5. 是否存在密钥、依赖、权限或数据风险。

不要修改代码。把审核结果写入 REVIEW 文档。
~~~

Codex 自己的 Review 可以作为第一层独立检查。严格任务如果 Codex 是作者，最终审核优先交给 Claude Code 或 Cursor，减少同一模型既写又审造成的盲区。

#### 17.3.8 Codex Hooks 与机器门禁

可信项目可以使用项目级 Codex Hooks，在生命周期节点执行检查，例如：

- 命令运行前检查高风险操作。
- 文件修改后执行格式或快速检查。
- 任务结束前检查任务文档和验证证据。
- 阻止未经授权的推送或发布命令。

Hooks 只能作为即时拦截层。HGAI 的最终证据仍然来自项目统一验证入口、Git 检查点和远端 CI，不能因为 Hook 文件存在就宣布验证完成。

### 17.4 与 Claude Code 结合使用

#### 17.4.1 配置 Claude Code 入口

Claude Code 的默认项目入口是 <code>CLAUDE.md</code>，不会仅因为项目里存在 <code>AGENTS.md</code> 就完整按照 HGAI 工作。

在项目根目录创建：

~~~markdown
@AGENTS.md

# Claude Code 项目入口

开始任务前必须读取：

1. docs/INDEX.md
2. docs/rules/INDEX.md
3. docs/coordination/ACTIVE_TASKS.md
4. 与本任务相关的模块地图、术语表和任务文档

任何写入前必须：
- 建立或认领任务；
- 用终端用户语言说明计划；
- 等待需要的人类确认；
- 明确验证方法。

不得复制 docs/rules 中的规则到这里。
docs/rules 是规则的唯一权威来源。
~~~

也可以把现有 [Claude Code 适配器](adapters/CLAUDE.md) 复制为项目根目录 <code>CLAUDE.md</code>，但应在开头增加：

~~~markdown
@AGENTS.md
~~~

Claude Code 支持通过 <code>@文件路径</code> 引入其他说明文件。可以用 <code>/context</code> 检查当前实际载入的项目说明。参见 [Claude Code：项目记忆与 CLAUDE.md](https://code.claude.com/docs/en/memory)。

根 <code>CLAUDE.md</code> 应保持简洁，只存工具入口和 Claude Code 特殊约束。完整项目事实和规则仍保存在 HGAI 的权威文档中。

#### 17.4.2 使用 Claude Code 的 Plan Mode

高风险任务不要直接进入可写模式，可以启动：

~~~powershell
claude --permission-mode plan
~~~

或者在会话中用 <code>Shift+Tab</code> 切换到 Plan Mode。

Plan Mode 允许 Claude 阅读和分析项目，但不直接修改文件，适合：

- 生成任务计划。
- 确认责任模块。
- 分析现有实现。
- 设计测试方法。
- 审查其他 AI 的代码。
- 发现需求与代码之间的冲突。

参见 [Claude Code：常用工作流](https://code.claude.com/docs/en/common-workflows)。

输入：

~~~text
按照 HGAI 严格模式分析以下需求。

先读取项目入口、规则、术语表、模块地图和活动任务。
只做计划，不修改代码。

请用终端用户语言告诉我：
1. 要增加什么功能。
2. 用户从哪里使用。
3. 页面或操作流程会怎样变化。
4. 会影响哪些既有功能。
5. 怎样证明功能已经完成。

同时在任务文档中记录技术实施范围、测试计划和 Git 基线。
~~~

项目负责人只审核前面五项；详细技术部分可留给第二个 AI。

#### 17.4.3 确认后进入实施模式

确认计划后，切换回默认模式，然后说：

~~~text
任务计划已经确认。

请严格按照已批准的任务文档执行：
- 不扩大范围；
- 不修改未列入计划的模块；
- 如果发现计划需要改变，立即暂停并说明；
- 功能和自动化测试必须同批完成；
- 执行真实验证；
- 不允许把“代码看起来正确”写成“验证通过”。
~~~

如果实际情况与计划不一致，Claude 应停止并返回：

- 发现了什么。
- 为什么原计划不能继续。
- 对终端用户会产生什么影响。
- 需要项目负责人决定什么。

#### 17.4.4 使用 Claude Code 权限机制

HGAI 是行为规则；Claude Code 的权限配置则是机器约束。两者要同时使用。

例如在 <code>.claude/settings.json</code> 中设置：

~~~json
{
  "permissions": {
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(git reset --hard *)"
    ]
  }
}
~~~

含义是：

- 推送远端前必须请求确认。
- 不允许读取密钥文件。
- 不允许执行破坏性的强制回退。

具体命令应根据项目实际情况调整。Claude Code 权限遵循 <code>deny → ask → allow</code> 的优先顺序。参见 [Claude Code：权限配置](https://code.claude.com/docs/en/permissions)。

不要在真实项目中随意使用跳过权限检查的模式，特别是包含生产密钥、远端部署权限或用户数据的项目。

#### 17.4.5 使用 Hooks 做自动检查

Claude Code 可以在 <code>.claude/settings.json</code> 中配置 Hooks，例如：

- 修改文件后运行格式检查。
- 结束任务前运行快速测试。
- 执行 <code>git push</code> 前阻止并要求确认。
- 检测到疑似密钥时中止操作。
- 检查任务文档是否存在。

Hook 返回特定阻止状态时，可以拦截操作。参见 [Claude Code：Hooks](https://code.claude.com/docs/en/hooks-guide)。

不过 Hooks 不是最终证据。完整验证仍应由以下机制共同完成：

- 项目测试。
- 构建命令。
- 密钥扫描。
- 依赖检查。
- Git pre-commit。
- 远端 CI。

#### 17.4.6 Claude Code 并行任务

Claude Code 可以通过独立 Worktree 启动任务，例如：

~~~powershell
claude --worktree feature-order-cancel
~~~

使用前仍要先认领 HGAI 任务。不要仅依靠 Worktree 名称判断任务是否冲突；应检查 <code>ACTIVE_TASKS.md</code> 中的责任模块和预计写入文件。

多个 Claude 会话可以并行调查不同模块，但同一任务只保留一个写入者。调查型会话输出证据和建议，不能未经认领直接修改作者正在处理的文件。

#### 17.4.7 用 Claude Code 做第二审核者

打开一个新的只读会话：

~~~powershell
claude --permission-mode plan
~~~

然后输入：

~~~text
你现在是 HGAI 独立技术审核者。

审核目标：
- 任务 ID：<task-id>
- Commit：<commit-id>
- 作者：Codex 或 Cursor

要求：
1. 不修改任何代码。
2. 对照任务文档、用户验收标准、模块地图和测试规则。
3. 检查是否修改了无关模块。
4. 检查自动化测试是否真正覆盖用户行为。
5. 检查验证记录是否来自实际命令。
6. 把问题按严重程度写入 REVIEW 文档。
7. 最后用非程序员也能理解的语言说明：
   - 功能是否可用；
   - 用户可能遇到什么问题；
   - 是否建议合并或发布。
~~~

审核目标必须绑定具体 Commit。不能只说“审核刚才的代码”，否则作者继续修改后，审核结论和实际代码将不再对应。

### 17.5 与 Cursor 结合使用

#### 17.5.1 配置 Cursor 项目规则

Cursor 可以读取项目根目录和子目录中的 <code>AGENTS.md</code>，因此仍然保留 HGAI 根入口。

另外，把 [ai-project-control.mdc](adapters/ai-project-control.mdc) 复制到目标项目：

~~~text
.cursor/rules/ai-project-control.mdc
~~~

它应保留：

~~~yaml
---
description: HGAI project control entry
alwaysApply: true
---
~~~

Cursor 项目规则必须使用 <code>.mdc</code> 扩展名。单纯把普通 <code>.md</code> 文件放入 <code>.cursor/rules/</code>，Cursor 不会把它当作项目规则加载。参见 [Cursor：Project Rules](https://cursor.com/docs/rules)。

HGAI 的完整规则仍然保存在：

~~~text
docs/rules/
~~~

<code>.cursor/rules/ai-project-control.mdc</code> 只负责告诉 Cursor 去读这些规则，不要把完整规则复制成多份，否则以后很容易出现：

- HGAI 规则已经更新。
- Cursor 规则还是旧版本。
- Claude 又使用第三个版本。
- 三个 AI 得出不同结论。

#### 17.5.2 为不同模块配置 Cursor 规则

例如只对支付模块生效：

~~~yaml
---
description: 支付模块的安全和验证要求
globs:
  - "src/payment/**"
  - "tests/payment/**"
alwaysApply: false
---

进入支付模块前，必须读取：
- docs/system/payment.md
- docs/rules/security.md
- docs/rules/testing.md

任何接口、金额计算、状态变化都必须有自动化测试。
不得用默认成功、静默重试或吞掉错误作为兜底。
~~~

模块规则只存放模块特殊约束。全项目通用规则继续由 HGAI 根入口负责。

#### 17.5.3 使用 Cursor Plan Mode

打开 Cursor Agent 后，通过 <code>Shift+Tab</code> 进入 Plan Mode，然后输入 HGAI 严格任务提示词。

Cursor 会生成可编辑计划。不要只把计划留在聊天记录里，应使用“Save to workspace”，保存为：

~~~text
docs/tasks/active/<任务ID>-<简述>.md
~~~

这样即使：

- 关闭 Cursor。
- 换成 Codex。
- 换成 Claude Code。
- 第二天重新开始。
- 更换模型。

任务计划仍然存在于项目中。参见 [Cursor：Plan Mode](https://cursor.com/docs/agent/plan-mode)。

可以同时显式引用：

~~~text
@AGENTS.md
@docs/rules/INDEX.md
@docs/system/MODULE_MAP.md
@docs/system/GLOSSARY.md
@docs/coordination/ACTIVE_TASKS.md
~~~

然后提出需求。

#### 17.5.4 Cursor 计划确认后的执行

计划确认后点击 Build，或者切换到 Agent 模式：

~~~text
计划已经批准。

请严格按照已保存的任务文档执行。
如果需要改变责任模块、修改路径或用户行为，先暂停并重新申请确认。
实现完成后必须：
1. 补充自动化测试。
2. 执行统一验证脚本。
3. 记录命令、退出状态和结果。
4. 提交带任务 ID 的 Commit。
5. 更新任务和完成报告。
~~~

Cursor 很适合实时查看修改过程，但不要把“编辑器显示没有红线”当成完成证据。

真正的完成证据仍然是：

- 测试通过。
- 类型检查通过。
- 构建通过。
- 安全检查通过。
- CI 通过。
- 指定 Commit 被独立审核。

#### 17.5.5 使用 Cursor 审核

Cursor 可以使用 Find Issues 或 Agent Review，对当前变化或相对主分支的修改进行审核。参见 [Cursor：Reviewing and Testing](https://cursor.com/learn/reviewing-testing)。

审核时使用：

~~~text
请只审核当前分支相对于 main 的变化，不修改文件。

审核依据：
@AGENTS.md
@docs/rules/INDEX.md
@当前任务文档
@模块地图
@测试规则

检查：
- 用户验收标准是否真正满足；
- 页面变化是否符合计划；
- 是否影响无关功能；
- 是否缺少测试；
- 是否引入重复实现；
- 是否存在密钥、依赖、权限和数据风险；
- 完成报告是否夸大了验证状态。
~~~

如果 Cursor 是代码作者，最好让 Codex <code>/review</code> 或 Claude Code Plan Mode 做最终独立审核。AI 自己审自己的工作，可以作为第一遍检查，但不应成为严格任务的唯一审核证据。

#### 17.5.6 Cursor Hooks

Cursor 支持项目级 <code>.cursor/hooks.json</code>，可以在以下时机执行检查：

- 命令执行前。
- 文件编辑后。
- Agent 准备结束时。
- 执行敏感操作前。

项目 Hooks 可以随仓库版本管理，也能被远端 Agent 使用。参见 [Cursor：Hooks](https://prod.cursor.com/docs/hooks)。

适合加入：

- 禁止无任务 ID 的提交。
- 禁止未经确认的 <code>git push</code>。
- Agent 结束前执行快速验证。
- 扫描疑似密钥。
- 检查活动任务是否已经登记。

但 Hook 失败可能受具体事件和退出方式影响，所以 CI 仍是最终机器关卡。

#### 17.5.7 Cursor Cloud 或 Background Agent

如果使用 Cursor 的远端或后台 Agent，应当把每个任务放在独立分支并通过 PR 返回结果。启动远端任务前先在中央任务表中认领范围，不能等远端 Agent 完成后才登记。

远端 Agent 运行在独立环境中，不能默认拥有本地未提交文件、个人密钥或本机服务。任务说明必须提供：

- 任务 ID 和目标分支。
- 用户功能和验收标准。
- 责任模块和禁止范围。
- 环境准备方式。
- 允许使用的测试和构建命令。
- 不得访问或输出的敏感数据。
- 完成后必须提供的 Commit、CI 和审核证据。

### 17.6 三款 AI 协同使用

最稳妥的组合不是让三个 AI 同时写同一项功能，而是分离角色。

| 任务作者 | 推荐审核者 |
|---|---|
| Codex | Claude Code Plan Mode |
| Claude Code | Codex <code>/review</code> |
| Cursor | Codex <code>/review</code> 或 Claude Code |
| 任意 AI | Cursor Agent Review 可作为附加检查 |

#### 17.6.1 一个任务只能有一个写入者

在 <code>ACTIVE_TASKS.md</code> 登记：

~~~text
任务：TASK-20260830-153012-CODEX-A3F7
责任模块：订单详情
写入者：Codex
审核者：Claude Code
分支：feature/order-copy
状态：实施中
~~~

Claude Code 和 Cursor 可以读取、分析、审核，但不得同时修改相同模块。

#### 17.6.2 审核必须锁定 Commit

不要说：

> 帮我审核刚才那些代码。

应当说：

> 审核任务 <code>TASK-...</code> 对应的 Commit <code>20d2ab5...</code>。

否则作者在审核过程中继续改代码，审核结论会失去明确对象。

#### 17.6.3 不能只在聊天里交接

交接至少包含：

- 任务 ID。
- 当前 Commit。
- 已完成的用户功能。
- 尚未完成的部分。
- 实际运行过的验证。
- CI 地址或结果。
- 当前风险。
- 下一步允许做什么。
- 下一位 AI 恢复后的第一条指令。

#### 17.6.4 状态必须分开写

不要笼统地写“已经完成”。应区分：

~~~text
功能实现：完成
本地测试：通过
远端 CI：通过
独立审核：通过
已合并主分支：否
已发布给用户：否
~~~

这样项目负责人不会把“本地写完”误解为“用户已经能使用”。

#### 17.6.5 推荐交叉组合

推荐的实际执行组合：

- Codex 负责编码，Claude Code Plan Mode 对指定 Commit 只读审核。
- Claude Code 负责编码，Codex <code>/review</code> 对指定 Commit 审核。
- Cursor 负责前端或交互实现，Codex 或 Claude Code 审核业务边界、测试和回归风险。
- 同一 AI 的内置 Review 作为第一遍检查，另一个 AI 作为严格任务的最终技术审核者。
- 项目负责人始终只审核用户功能、使用过程、可见变化、用户收益和高影响授权。

### 17.7 完整任务实例

假设需求是：

> 给订单详情页增加取消订单功能。

#### 第一步：项目负责人提出需求

项目负责人只需要用正常语言描述：

~~~text
未发货订单需要能够取消。
用户点击取消后要二次确认。
取消成功后，订单状态应立即变化，并明确告诉用户退款会怎样处理。
已发货订单不能取消。
~~~

#### 第二步：作者 AI 建立任务和认领

作者 AI 应当：

1. 读取项目入口、规则、模块地图、术语表和活动任务。
2. 生成唯一任务 ID。
3. 检查订单、支付、退款模块是否被其他任务占用。
4. 在 <code>ACTIVE_TASKS.md</code> 登记责任范围。
5. 创建任务文档。
6. 记录当前分支、工作区状态和基线 Commit。

#### 第三步：作者 AI 生成用户语言计划

AI 应当先反馈：

> 我会在符合条件的订单详情页增加“取消订单”入口。用户点击后先看到确认窗口，确认后页面会显示新的订单状态和退款说明。已经发货的订单不会显示可取消入口。本次不会改变支付金额、发货流程或其他订单。

项目负责人确认这个结果即可。

#### 第四步：AI 在任务文档中记录技术内容

技术内容由 AI 填写，例如：

- 责任模块。
- 订单状态转换。
- 取消接口调用。
- 数据一致性。
- 并发取消。
- 重复操作防护。
- 退款说明来源。
- 自动化测试。
- 验证命令。
- 回滚方法。

项目负责人不需要逐行理解代码。第二个 AI 负责复核技术范围、模块边界和验证设计。

#### 第五步：AI 实现并验证

机器证据应包括：

~~~text
取消未发货订单测试：通过
已发货订单禁止取消测试：通过
重复点击取消测试：通过
接口失败时页面提示测试：通过
订单状态刷新测试：通过
完整构建：通过
密钥扫描：通过
远端 CI：通过
~~~

没有实际执行的项目不能填写“通过”。如果项目尚无某种测试，必须写明缺口、临时人工验收步骤和后续自动化任务。

#### 第六步：作者建立 Git 检查点

在获得授权后提交：

~~~text
[TASK-20260830-153012-CODEX-A3F7] add user-facing order cancellation
~~~

任务文档记录该 Commit。远端推送后，CI 结果也必须绑定同一个 Commit。

#### 第七步：第二个 AI 审核

审核者只读检查：

- 是否能取消不该取消的订单。
- 是否可能重复退款。
- 页面是否在接口失败时错误显示成功。
- 失败时是否吞掉错误。
- 是否修改了无关的支付或发货模块。
- 测试是否真的覆盖用户操作。
- 完成报告是否把本地完成夸大成已经发布。

发现问题时，审核者写入 <code>REVIEW.md</code> 并退回作者。审核者不顺手修改代码。

#### 第八步：最终向项目负责人汇报

好的完成报告应当是：

> 现在，尚未发货的订单可以从订单详情页取消。用户点击“取消订单”后会先看到确认提示，确认成功后页面立即显示订单已取消，并展示退款处理说明。已发货订单不会出现取消入口。我们还验证了重复点击、接口失败和订单状态刷新等情况。该功能已经通过本地测试和远端 CI，但尚未发布到正式环境。

不应当把主要篇幅写成：

> 重构了订单状态机，新增 service method、DTO、hook、mutation 和 reducer……

技术细节可以附在维护记录里，但不应成为对项目负责人的主要汇报。

### 17.8 快速模式与严格模式的实际选择

#### 最小可用配置

个人项目刚开始使用 HGAI 时，至少启用：

- 根 <code>AGENTS.md</code>。
- <code>PROJECT.md</code>、<code>MODULE_MAP.md</code> 和 <code>GLOSSARY.md</code>。
- <code>TASK_LITE.md</code>。
- 一个统一验证命令。
- Git 任务 ID。
- 终端用户语言完成报告。

#### 完整严格配置

重要或长期项目增加：

- <code>ACTIVE_TASKS.md</code>。
- 独立分支或 Worktree。
- 自动化测试与远端 CI。
- 密钥和依赖扫描。
- 权限配置和 Hooks。
- 第二 AI 只读审核。
- <code>REVIEW.md</code>、验证证据和交接文档。
- 分支保护。
- 文档防腐和规则沉淀。

#### 建议选择

- 日常小任务：Cursor 或 Codex 实施，使用 <code>TASK_LITE</code>。
- 跨模块功能：Codex Worktree 或 Claude Code Plan Mode 先规划。
- 高风险功能：Claude Code 或 Codex 实施，另一个 AI 锁定 Commit 只读审核。
- 前端页面调整：Cursor 实施较直观，Codex 或 Claude Code 复审。
- 架构重构：先由一个 AI 出方案，第二个 AI 只读审方案，确认后再编码。
- 发布前：必须以 CI、测试和目标 Commit 为依据，不以聊天中的“我已经检查过”为依据。

### 17.9 最容易用错的地方

1. 只复制框架文件，不根据真实项目填写内容。
2. 把整套规则分别复制到 <code>AGENTS.md</code>、<code>CLAUDE.md</code> 和 Cursor Rules，导致三份规则漂移。
3. 在聊天里批准计划，但没有把计划保存进仓库。
4. 多个 AI 同时修改同一模块，没有任务认领。
5. 审核时没有锁定具体 Commit。
6. AI 声称“测试通过”，但没有命令、退出状态和 CI 证据。
7. 把本地实现、CI 通过、合并和发布混成一个“已完成”。
8. 让审核者发现问题后直接修改，导致作者和审核责任再次混合。
9. 项目负责人被迫审核函数、接口和依赖方向，却没有看到用户功能如何变化。
10. 为了节省时间允许 AI 使用兜底、静默失败、兼容分支或重复实现掩盖根因。
11. 为每个任务扫描整个仓库，没有先使用模块地图和定位阶梯。
12. 文档只增加不归档，最终让旧信息污染新任务。

### 17.10 核心使用结论

Codex、Claude Code 和 Cursor 可以轮换，但项目规则、任务计划、验证证据和用户需求不能跟着聊天窗口一起消失。它们必须留在仓库里，成为下一位 AI 可以继续使用的项目事实。

HGAI 最终建立的是以下责任关系：

- 人提出真实用户需求、确认用户结果并授权高影响动作。
- 作者 AI 负责计划、实现、测试和记录。
- 第二 AI 负责只读技术复核。
- Git、测试、扫描和 CI 负责给出机器证据。
- 项目文档负责跨会话、跨模型和跨工具保存项目认知。
- 所有对项目负责人的主要反馈，都先说明终端用户获得了什么功能、怎样使用、页面或行为发生了什么变化，以及最终带来了什么结果。
